## B1 — Trending's Day window scores 0 on every row {#b1}

**Severity** S1 — the default view of a shipped feature is always empty of data.

**Symptom.** `/trending` opens on Day. Every row reads `0`:

```
1  #bbcnews    12 posts   0
2  #nevada      2 posts   0
3  #wildfires   2 posts   0
   … 17 tags, all 0
```

Week works and is fully populated — 80 tags, `#bbcnews` scoring 25,529,868
across 46 posts.

**Evidence.** Straight from `data/app.db`:

```
posts taken in the last 24h : 31 total, 27 with NULL like_count   (87%)
posts taken 1-7 days ago    : 94 total, 19 with NULL like_count   (20%)
```

The split follows `discovered_at`, not age:

```
spotify DccIqhvARrV  taken 08-24T22:28  likes=18200  discovered 08-25T09:12
bbcnews DcbyVnIFWcY  taken 08-24T19:13  likes=None   discovered 08-24T19:30
bbcnews Dcbt9WRjR0j  taken 08-24T18:35  likes=None   discovered 08-24T19:30
nasa    Dcbo8HCGWep  taken 08-24T17:51  likes=None   discovered 08-24T19:56
```

**Root cause.** Business Discovery serves newest-first and `next_cursor`
advances into older posts. A profile's newest posts are the ones it indexed
*first*, so they carry the oldest `discovered_at` — and the cursor has long
since walked past them. `handle_page_fetch` refreshes engagement only for posts
inside the page it fetches, so "Load more" heals progressively older rows and
can never come back to recent ones. Confirmed live: after four Load-mores the
Week window healed completely while Day did not move.

The only code that restarts a walk at the front is in `handle_profile_sync`:

```python
if row["next_cursor"] == "":          # exhausted -> restart at the front
    ... set next_cursor = NULL
elif row["next_cursor"] is not None:
    return                            # part-way: leave its cursor alone
```

`nike` is part-way, so re-syncing it never re-reads its recent posts. Verified:
nike synced 09:11, still 75/75 NULL afterwards.

**Not the ranking.** `api/app/services/hashtags.py` is correct — it is scoring
real nulls as zero, which is what it should do.

**Fix.** A backfill that pages from the front: reset `next_cursor` to `NULL`
before enqueueing `page_fetch`, or add a dedicated "refresh recent" action that
walks the first N pages regardless of cursor.

## B2 — Reel downloads waste ~10% of Meta's hourly quota each {#b2}

**Severity** S2 — a batch of ten reels would spend the whole hourly allowance on
calls that return nothing usable, then trip the breaker.

**Symptom.** Downloaded two nike reels (`DcG26tpx7WA`, `Db6EzJxRewC`). Both
succeeded. Meta app usage went **22% → 41%** for those two posts.

**Root cause.** `GraphAdapter.fetch_media` finds the cached url expired, raises
`_Stale`, and calls `_refresh`, which re-lists the owning profile up to
`IG_GRAPH_REFRESH_PAGES` (default 2) pages at roughly 4–5% of the hourly
allowance each. For a reel that re-listing is provably pointless — the adapter's
own error text says Business Discovery
"returns only a thumbnail for a reel, never the video itself" — so it always
falls through to the `yt-dlp` path anyway.

**What works.** Everything after the waste: the fallback fired, wrote
`full.mp4` (5.5 MB and 7.0 MB), spent the reel ledger correctly
(`0/20 → 2/20` hourly, `2/100 → 4/100` daily) and reported a real reset time.

**Fix.** In `fetch_media`, when the item is a reel and `self._reels` is present,
skip `_refresh` and go straight to the downloader.

## B3 — Refreshed CDN urls are thrown away {#b3}

**Severity** S2 — makes B2 recur per-post instead of once per page.

**Symptom.** After the two downloads above, `src_urls_at` for both posts is
still `2026-08-24T16:34:28`.

**Root cause.** `handle_media_fetch` passes a `MediaHint` in; the adapter
re-lists and receives fresh urls *for the whole page*; the handler then writes
only `media_files` rows and `full_status`. The refreshed `src_urls` are never
persisted, so the next stale post from the same page pays the same two-page
cost having already been handed the answer.

**Fix.** Persist the refreshed sources (and `src_urls_at`) for every post the
refresh listing returned, not just the one being fetched.

## B4 — Download always fails on the first click {#b4}

**Severity** S1 — the primary action of the app's headline flow.

**Symptom.** The selection sider shows a Base filename box containing
`nike_ss26`. Pressing "Download 3 files" returns an inline error,
"Enter a base filename first.", with a Retry button.

**Evidence.** The suggestion is a placeholder, not a value:

```js
document.querySelector('[data-testid="base-filename"]')
// { value: "", placeholder: "nike_ss26", valueLen: 0 }
```

The button is enabled regardless, so every download costs a wasted click and an
error message — while the name the app itself suggested sits unused.

**Fix.** Seed the input's value with the suggestion, or disable Download until
the field is non-empty. `web/components/SelectionBar.tsx`.

**Two nits found alongside it**

- The "Enter a base filename first." alert is not cleared once a name is typed;
  it sits under a now-valid form.
- The filename preview shows the raw name — `soak run 01_01 through
  soak run 01_03` — but files are written sanitised, `soak_run_01_01.jpg`.

## B5 — A `ready` item with no thumb row is a permanently broken tile {#b5}

**Severity** S3 — one grid tile is broken forever, and the only repair destroys
every downloaded original for the profile.

**Symptom.** nike `DatCfJgRCD6` renders as a broken image in POSTS, SAVED and
cached-only views.

**Evidence.**

```
data/media/nike/DatCfJgRCD6/thumb.jpg   exists, 465,971 bytes
media_files rows for it                 role='full' only — no 'thumb' row
GET /api/media/DatCfJgRCD6/thumb        404 {"message":"no thumbnail cached"}
```

**Root cause.** The existence check is on the filesystem while the truth the API
serves lives in the database. `handle_page_fetch` guards the thumbnail fetch
*and its row insert* with `if not thumb_dest.exists()`. The file is there, so
the block is skipped and the row is never re-inserted — re-syncing cannot heal
it. A crash between `download_to` and the `INSERT` leaves exactly this state,
and `worker/sweep.py` reconciles `.part` files and `full_status` but never a
finished file with a missing row.

**Only user-facing repair.** `DELETE /api/profiles/nike/cache`, which rmtree's
the profile's whole media directory.

**Fix.** Key the guard on the database row rather than the file, or extend the
boot sweep to re-insert rows for files it finds on disk.

## B6 — Recreate payloads ship `width: null, height: null` {#b6}

**Severity** S3 — defeats the stated purpose of the payload.

**Symptom.** `/recreate/DcVY5dZm_Pv` prepares this:

```json
{ "index": 1, "path": "nike/DcVY5dZm_Pv/full_1.jpg",
  "mime": "image/jpeg", "bytes": 1693666,
  "width": null, "height": null }
```

3 of 7 `role='full'` rows in the database have NULL dimensions.

**The probe is fine.** Run directly against those exact files:

```
full_1.jpg (1620, 2160)   full_2.jpg (1620, 2160)
full.jpg   (1350, 1687)   full.mp4   (720, 1280)
```

**Root cause.** Those rows were written by a build that predated probing, and
nothing re-probes a file already on disk. "Prepare again" healed a stale
single-slide payload to both slides but left the dimensions NULL, because it
reads `media_files` rather than the files.

`api/app/probe.py`'s own docstring: a payload that cannot say how big a picture
is "forces whoever receives it to open every file to find out" — which is
exactly what these payloads do.

**Fix.** Re-probe on prepare when a row's dimensions are NULL and the file
exists, and backfill existing rows.

## B7 — Switching adapter resets the Meta quota reading to 0% {#b7}

**Severity** S3 — the guard that prevents a rate-limit is briefly blind, and the
displayed number is wrong.

**Symptom.** Meta usage read 41%. `POST /api/adapter {"adapter":"fake"}` then
back to `"graph"`, and `GET /api/status` reports `usage: 0.0`; the header shows
"API 0%". Still showing 0% minutes later, because no Graph call has happened
since.

**Root cause.** The switch constructs a new `GraphAdapter`, so `_usage` and
`_usage_peak` reset to `0.0`. `_usage_peak` is the value
`IG_GRAPH_USAGE_LIMIT` (90%) guards against, so the backoff is disabled until
the first Graph response restores a real `x-app-usage` reading — and that first
call is exactly the one that could tip a throttled app over.

**Fix.** Carry the usage readings across a swap, or persist them outside the
adapter instance.

## B9 — Signed CDN urls are written to the log in full {#b9}

**Severity** S4.

## B10 — A long base filename crashes the download endpoint {#b10}

**Severity** S2 — unhandled exception on ordinary user input, and the failure
handler fails too.

**Repro.**

```
POST /api/downloads {"shortcodes":["DatCfJgRCD6"], "base": "a"*300}
-> HTTP 500, body "Internal Server Error"
```

**Traceback.** `paths.atomic_write` cannot open the `.part` file:

```
OSError: [Errno 22] Invalid argument:
  '..\downloads\aaaa…aaa_01.jpg.part'
During handling of the above exception, another exception occurred:
OSError: [WinError 123] The filename, directory name, or volume label
  syntax is incorrect: '..\downloads\aaaa…aaa_01.jpg.part'
```

The second error is the cleanup path — `part.unlink(missing_ok=True)` in the
`except BaseException` block fails on the same too-long path, so the handler
that exists to tidy up raises on its way out.

The frontend cannot say anything useful about this. `web/lib/api.ts` already
anticipates it: FastAPI answers an unhandled exception with the plain text
"Internal Server Error", so the user sees
`500 Internal Server Error: Internal Server Error`.

**Fix.** Cap the sanitised base in `paths.sanitize_base` (a component budget of
~200 chars leaves room for the `_NN` suffix and the extension), and return 400
rather than letting `OSError` escape. Guard the `.part` cleanup with its own
`try`.

**Related, from reading `services/downloads.py`.** `run()` copies files in a
loop with no rollback, so a failure part-way through a multi-post batch leaves
the earlier files written and still answers 500. Not reproduced here — the
length failure hits the first file — but a missing source file (a cache
directory deleted by hand) would take that path.

## B11 — Non-Latin base filenames are silently deleted {#b11}

**Severity** S3 — silent data loss in a value the user typed.

**Repro.**

```
base "नाइकी 2026"  -> written "2026_01.jpg"       Devanagari dropped
base "...///***"   -> written "download_01.jpg"   correct fallback
base "../../../../evil" -> written "evil_01.jpg"  correct, contained
```

A base that is *entirely* non-Latin collapses to the `download` fallback, so
two different batches named in Hindi, Arabic or Japanese overwrite into the
same `download_NN` series (well — `download_NN-1`, since collisions are
suffixed, but the user's name is gone either way).

**Root cause.** `paths.sanitize_base` collapses on `[^A-Za-z0-9]+`.

This is worth fixing because the codebase is otherwise careful here:
`services/hashtags.py` explicitly avoids `\w` so that `#नाइकी` is not cut at
its first vowel sign, and documents why. The filename path never got the same
treatment.

**Fix.** Keep Unicode letters, numbers and marks — the same category test
`hashtags._body` already uses — and strip only path separators, control
characters and the Windows-reserved set.

## B12 — One user action can write two `lookup` rows {#b12}

**Severity** S3 — the activity log is the app's audit trail; it should not
double-count.

**Symptom.** Pairs of identical rows at the same second:

```
2026-08-24 19:56:08  lookup  nasa
2026-08-24 19:56:08  lookup  nasa
2026-08-24 19:41:27  lookup  natgeo
2026-08-24 19:41:27  lookup  natgeo
2026-08-24 22:36:52  lookup  meta
2026-08-24 22:36:52  lookup  meta
```

**Root cause.** In `routes/profiles.py`:

```python
job_id = queue.enqueue_unique(conn, "profile_sync", {"username": username})
activity.record(conn, "lookup", username, None)
```

`enqueue_unique` correctly returns `None` for a duplicate, but `activity.record`
runs unconditionally, so two rapid `POST /sync` calls produce one job and two
log rows. The profile page's own effect plus a search-box submit (or a
double-invoked effect in dev) is enough to trigger it.

**Fix.** Either record only when a job was actually enqueued, or keep recording
every lookup deliberately and say so — but not both by accident.

## Not a bug — recorded so it is not re-investigated

**Preview appeared dead in four of five tabs.** The lightbox does open; a
background tab just never paints it. `document.visibilityState` was `"hidden"`
while `document.querySelectorAll('.ant-modal').length` was `1`. Chrome throttles
`requestAnimationFrame` in hidden tabs, so rc-motion never runs. Verified
working in the foreground tab: carousel 1 of 2 → Next → 2 of 2, caption pane,
Instagram link. The same cause left two "Preview" tooltips stuck on screen.

Any modal-based UI in a background tab has to be checked through the DOM rather
than a screenshot.

**Light theme looked unreadable.** It is not. A full-viewport screenshot of the
activity table made the text look washed out; zoomed in, the contrast is fine —
black headers, dark body text, grey secondary. JPEG downscaling, not the theme.

## Verified working against live data

Five profiles driven concurrently through one worker with no interleaving
errors. Deep-link `/p/<user>` self-queues a sync and names the profile while
loading. Warm profiles served from cache with zero Graph calls. Auto tab-pick
(REELS for natgeo/bbcnews/spotify, POSTS for nike/adidas). Caption search,
cached-only, SAVED, Reset. Lightbox carousel navigation. Selection sider
counts ("2 selected · 3 files · 1 already cached"). Download naming —
`soak_run_01_01.jpg`, `_02a`, `_02b`, sanitised, oldest-first, carousel
lettered — plus its activity row. Load-more 12 → 48. Recreate mark, idempotent
re-mark, `409` on preparing an undownloaded post, `400` on unknown window and
unknown adapter. Adapter switch with filesystem-isolated datasets (nike: 8
items on fake, 75 on graph) and an honest `usage: null` on fake.

Worker ran the whole session, breaker never tripped, queue always drained, zero
retries, zero failures. Tabs after 8–23 minutes: heap 84–91 MB, polling live,
no drift. Backend suite re-run mid-soak: **338 passed, 4 skipped**.

**Second round — error paths and edges.** Twenty error responses checked, all
correct and all specific:

| Case | Result |
|---|---|
| unknown profile | 404 with `last_error` from the failed sync job |
| media / load-more / tracked on unknown profile | 404 `unknown profile` |
| `ensure` unknown shortcode | 200, status `unknown` (not an error) |
| full of an uncached post | 404 `not cached` |
| preview of unknown post | 404 `no sources recorded` |
| download with no items | 400 `no items selected` |
| download of a not-ready item | 409 listing them in `not_ready` |
| recreate unknown shortcode | 200 with it in `unknown` |
| prepare bad slide index | 400 `no such slide: 99`, `available: [1,2]` |
| limit/offset out of bounds (5 variants) | 422 naming the field and the bound |

**Path traversal is contained.** `base: "../../../../evil"` wrote
`downloads/evil_01.jpg`; nothing appeared outside the output directory.

**Name collisions never overwrite.** A second download with the same base wrote
`evil_01-1.jpg` alongside `evil_01.jpg`.

**Offset paging is stable.** Four pages of five over nike returned 20 unique
shortcodes, byte-identical to one page of twenty.

**Tag lookup normalises.** `bbcnews`, `%23bbcnews` and `BBCNEWS` all resolve to
the same 46 posts; a tag nobody used returns an empty list, not a 404.

**Trending → recreate queue.** Expanded `#bbcnews` in the Week window, picked
two thumbnails, pressed Mark for recreate: both showed the `queued` label and
the server queue went 10 → 12 with the right usernames.

**Saved selections persist.** Named a two-tile selection; `localStorage` under
`instascraper:selections:nike` held
`[{"name":"my picks","shortcodes":["DcVY5dZm_Pv","DZ76oS7m4G0"]}]`.

**Recreate tab navigation.** A tile in the profile's RECREATE tab routes to
`/recreate/<shortcode>`, which renders the six-slide picker, an honest
"Not downloaded yet — submitting will fetch it", and the "No generator
connected yet" notice.

**Engagement overlay** renders on tiles that have data (`596K` likes,
`3.1K` comments), and is absent rather than zeroed on tiles that do not.
