01 · Overview

What it is

Instagram rate-limits by IP and caps anonymous browsing at roughly a dozen recent posts. Getting full-resolution media reliably needs a login, and a login you care about is not something you want a scraper hammering. Instascraper puts one dedicated account behind one serialized request path, and gives you a grid to pick from.

It is deliberately small. Public profiles only. Read-only — it never writes to Instagram. No scheduled crawling, no full-history archiving in one pass. One user: yours.

Browse cheaply

A lookup fetches post metadata and small thumbnails only. Full-resolution media is never touched until you ask for it.

Download deliberately

Select one, several, or all. Files land in your output folder as base_01.jpg, base_02.mp4 — individually, never zipped.

One identity, one queue

Every Instagram-bound request goes through a single worker thread with an enforced gap between calls. Not a convention — a structural property.

Cache forever

Fetched media stays on disk. Re-selecting something you already pulled completes in under a second and queues nothing.

02 · The download flow

Three stateless calls, no job table

Pressing Download does not create a server-side download record. The browser drives a three-step conversation, and the same endpoint that enqueues work is the one that reports progress.

  1. POST /api/media/ensure

    Send the selected shortcodes. The server returns a status per item and enqueues a media_fetch job for anything not yet cached. Idempotent — calling it again never double-enqueues.

  2. Re-poll the same endpoint every 1.5 s

    The response doubles as the progress feed: 4 ready · 6 fetching · 2 queued. No websocket, no SSE — one user, three endpoints.

  3. POST /api/downloads

    Once everything reads ready, the server copies the cached files into your output folder with generated names, writes one activity row, and returns the paths.

The tab drives this. Close it mid-wait and the flow stops — but the media_fetch jobs still finish and the media stays cached, so reopening and re-selecting completes instantly. Nothing is lost beyond a repeated click. That tradeoff buys you no downloads table and no second assembler thread.

How files get named

Selections are ordered oldest first, so a numbered sequence reads chronologically. This is deliberately the opposite of the grid, which shows newest first.

8 posts selected, two of them 3-slide carousels

  set_01.jpg   set_02.jpg   set_03.jpg   set_04.jpg
  set_05.jpg   set_06.jpg
  set_07a.jpg  set_07b.jpg  set_07c.jpg   <- carousel
  set_08a.jpg  set_08b.jpg  set_08c.jpg   <- carousel

12 files

Base filenames are sanitized to alphanumerics and underscores, so ../../escape becomes escape and can never leave the output directory. An existing file is never overwritten — a collision gets -1, -2, and so on.

03 · Architecture

Two containers, one thread that matters

--workers 1 is load-bearing. A second process would mean a second worker thread, and the whole rate-limit strategy would quietly stop holding.

Job kinds

All three run on the same worker. Only pickup order differs — and it differs because you are waiting on some of them and not others.

KindPrioDoes
media_fetch10One shortcode to full-resolution file(s). You clicked Download; a spinner is on screen.
profile_sync20Resolve the profile, upsert the row and avatar, enqueue the first page.
page_fetch30Next PAGE_SIZE posts plus thumbnails. Background work behind "Load more".

Containing Instaloader

Instagram rotates the internal identifiers Instaloader depends on, and it breaks every few weeks regardless of pacing. That is ongoing maintenance, not a one-time integration — so the dependency is quarantined.

Everything that imports instaloader lives in api/app/ig/: the adapter and its rate controller, nothing else. The adapter exposes five functions returning plain dataclasses. A test walks the source tree and fails if any other module imports the library.

fetch_profile(username)              -> IgProfile
fetch_page(username, cursor, limit)  -> IgPage
fetch_media(shortcode, dest_dir)     -> list[SavedFile]
download_to(url, dest)               -> SavedFile
login()                              -> None

When Instagram changes something, the blast radius is one directory and its contract tests. classify() — which maps library exceptions onto the five cases the worker knows how to handle — is usually the first function that needs updating.

05 · Data model

Five tables

TableHolds
profilesOne row per looked-up account. next_cursor stores the frozen pagination iterator — NULL means never paged, '' means exhausted.
media_itemsOne row per post. full_status moves none → queued → fetching → ready, or failed with the error kept.
media_filesThumbnails, full media, and carousel children, uniformly. "Fully cached?" is COUNT(full rows) == child_count.
jobsThe queue. Claimed inside a transaction, ordered by priority then age.
activity_logYour history. A download is one row whose JSON detail carries the base name, count, output path, and shortcodes.

On disk

/data/media/<username>/<shortcode>/
    thumb.jpg      present after metadata fetch
    full.jpg       single post, child_idx 0
    full_1.jpg     carousel children, child_idx 1..N
    full_2.jpg

Every file is written as <name>.part and moved into place with os.replace(). A container killed mid-fetch leaves litter and a row stuck at fetching; startup sweeps both.

06 · Using it

From clone to first download

cp .env.example .env      # IG_USERNAME, IG_PASSWORD, OUT_DIR
docker compose build
docker compose run --rm api python -m app.ig.login
docker compose up -d

Open localhost:3000. Enter a username, browse the grid, click tiles to select — shift-click for a range, or Select all loaded. Type a base filename and press Download.

Why the login is a separate command

Two-factor prompts and checkpoint challenges cannot be solved headlessly. The entrypoint does the interactive login once and writes a session file into a volume that is deliberately separate from the media cache — so you can clear the cache without invalidating the login.

08 · Failure model

What happens when Instagram says no

The part that decides whether this thing survives. Every Instagram failure is classified into one of five cases, and each has exactly one response.

CaseResponse
Not found
Private		Terminal. Mark it, do not retry, say so plainly in the UI. Private accounts are out of scope by design.
429
rate limited		Temporary breaker trip. Worker sleeps IG_BACKOFF, queue intact, banner shows the resume time. The job is requeued without spending a retry — the failure was environmental, not the job's fault.
Challenge
dead session		Permanent breaker trip. Stays tripped until a human runs the login command. Automatically retrying past a challenge is how a throttled account becomes a flagged one.
Network
5xx		Retry with backoff, three attempts, then failed with the error kept on the row.
Anything elseLogged, job failed, worker survives. A bug in a handler must not take down the queue.
Empty grids and odd errors usually mean Instagram rotated something. Run pytest -m live. A failure there points at api/app/ig/adapter.py — the only file that should ever need to change for this class of break. The same code backs GET /api/health/canary, so the thing you run from the UI and the thing you run from a terminal cannot drift apart.
09 · Testing

142 tests, one of them allowed near the network

cd api && python -m pytest        # 127 backend, no network
bash scripts/e2e-native.sh        # 15 browser tests, no Docker
bash scripts/e2e.sh               # same suite via Compose (verified)
cd api && python -m pytest -m live   # opt-in, hits Instagram

The adapter boundary is what makes this testable: four call sites, plain dataclasses, and an in-memory fake underneath. Everything above it runs with zero network access.

The test that justifies the architecture

The fake records a start and end timestamp for every call. The worker test runs five jobs through it and asserts that no two call windows overlap and every gap clears IG_MIN_INTERVAL. That is the single property the whole design exists to guarantee, so it is asserted directly rather than inferred.

No HTTP cassettes

VCR-style recordings of Instaloader traffic would bake in session cookies and signed CDN URLs, and would keep passing green for weeks after the real API changed — precisely the failure they would exist to catch. Parser tests use checked-in sample payloads; the live canary covers the rest.

A green unit suite is not proof the thing runs. Three bugs shipped past a green unit suite and only appeared under a real server: FastAPI resolves a sync dependency and runs the sync endpoint on different threadpool threads, so a thread-local SQLite connection was used off-thread and every request 500'd; the fake adapter the server built was empty, so a seeded database referenced posts it had never heard of; and the boot log advertised JSON while emitting a Python dict repr. TestClient runs on one thread and never reads the logs, so it could see none of them. All three now have regression tests.

Known gaps, stated plainly

  • The live canary has never run. It needs real credentials. Until it does, the adapter's agreement with today's Instagram is asserted only against checked-in fixtures — the one claim in this handbook with no evidence behind it.
  • The download flow depends on the tab staying open. Accepted tradeoff, documented above.
  • Failed items need a manual retry via ensure with retry: true. The API supports it; the UI exposes it only through the error state's Retry button.

Each phase ships through its own spec → plan → implement cycle; specs live in docs/superpowers/specs/, plans in docs/superpowers/plans/.
